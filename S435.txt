## Security / Limitations / Recommendations
- Webhook verification: `X-Webhook-Signature` header is used in the mock and service; real-world would use HMAC + timestamp + replay protection.
- Idempotency: service stores `transactionId` and uses it as primary dedupe key to ignore duplicate webhooks.
- Race conditions: when webhook and polling (if implemented) or repeated calls happen simultaneously, ensure `status` transitions are atomic in the persistence store.
- Sensitive values (3DS tokens) are not logged — avoid logging secrets in plaintext.
- Recommendations for production:
  - Implement real HMAC-signed webhooks and signature verification
  - Add idempotency-key headers to upstream calls
  - Implement metrics and telemetry: counters for fallback events, fraud alerts
  - Canary rollout: use `FEATURE_FLAG_USE_V2` in a service registry/feature-gate; start with a small percentage of traffic to v2
  - Add rate-limiting / circuit-breakers on upstream calls
