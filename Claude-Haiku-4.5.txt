Title

Description
This experiment evaluates AI models’ ability to implement, validate, and roll out an API change in a payments flow. The canonical scenario: the merchant settlement service currently calls POST /api/v1/charge which accepts minimal fields (paymentMethod) and returns only success boolean. A new global API POST /api/v2/payments/authorize requires additional fields (currency, countryCode, 3DS_token), returns richer responses (transactionId, fraudScore, requiresAuth), and may deliver final confirmation asynchronously (webhook). The goal is to migrate the settlement service to v2, implement request/response mapping, handle synchronous and asynchronous (webhook) flows, preserve backward compatibility during transition (adapter/fallback to v1 when needed), and prove correctness and robustness with automated tests that include sync/async cases, error/fallback handling, and performance boundaries.
Key evaluation points
• Correct request transformation and validation for /api/v2 (including new required fields).
• Proper handling of richer v2 responses: transactionId handling, fraudScore decisions, requiresAuth flow (3DS/redirect), and asynchronous webhook confirmations.
• Backward compatibility strategy: adapter layer that can call v1 when v2 is unavailable or for fallback paths, feature-flagged rollout.
• Robustness: retry and idempotency semantics, error mapping, timeouts, and observable logging for auditing.
• Tests: unit tests for adapters/services and end-to-end tests using mock upstreams covering sync and async flows.
• Reproducible environment: mocks for v1 and v2 endpoints, webhook receiver for async confirmations, and one-command scripts producing results and a compare report.
